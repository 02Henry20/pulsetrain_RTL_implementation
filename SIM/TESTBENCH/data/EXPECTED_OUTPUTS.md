# Golden Outputs And Module Examples

## Expected-event files

Each file in `expected/` contains one event per line:

```text
event_type frame_index x_pulses d_pulses
```

- Event type `0` is one consumed X/D output pair.
- Event type `1` is `FRAME_DONE`; its X/D fields are `00 00` placeholders.
- `frame_index` starts at zero and advances after each frame event.
- Pulse vectors are hexadecimal and use the RTL packing convention: lane 0 is the least-significant bit.

The files deliberately contain no comments or headers so the Verilog testbench can stream them with `$fscanf` and use little simulation memory.

## Sort

SORT rearranges D over time, independently for each lane. It preserves the number of ones in every D lane and packs those ones into the earliest temporal slices. X is never sorted and remains in its original temporal order.

For displayed bit strings below, the leftmost character is lane 3 and the rightmost is lane 0.

```text
input D:   t0 0100, t1 1001, t2 1001
output D:  t0 1101, t1 1001, t2 0000
```

Lane counts are `[lane3..lane0] = [2, 1, 0, 2]`, so the first output contains every lane with at least one pulse and the second contains every lane with at least two pulses. The corresponding X outputs are exactly `X(t0)`, `X(t1)`, and `X(t2)`.

## Zero delete

ZERO_DELETE removes a temporal pair when either vector has no active pulse. A crossbar update needs at least one X pulse and at least one D pulse.

```text
X=0101, D=0001 -> keep   (both vectors are nonzero)
X=0000, D=1110 -> delete (X is zero)
X=0010, D=0000 -> delete (D is zero)
```

It can therefore reduce a frame to zero outputs when no useful X/D coincidence exists.

## Group mask

GROUP_MASK groups temporal slices by identical D patterns. For each distinct D mask it accumulates how many times each X lane is active. During drain, one output layer is emitted for every required multiplicity; D remains the group mask on each layer.

```text
input:     t0 X=0101 D=0001
           t1 X=0010 D=0010
           t2 X=0010 D=0001

group D=0001: X counts [lane3..lane0] = [0,1,1,1]
output:    t0 X=0111 D=0001
           t1 X=0010 D=0010
```

The two `D=0001` slices merge because each accumulated X-lane count fits in one output layer. If both slices instead had `X=0101`, lanes 2 and 0 would each have count two, so one binary train cannot represent the sum:

```text
input:     X=0101 D=0001
           X=0101 D=0001
output:    X=0101 D=0001
           X=0101 D=0001
```

Grouping alone cannot reduce a nonempty frame below one output. Placing ZERO_DELETE first removes useless pairs before grouping and can reduce the entire frame to zero.

## LFSR

The LFSR emits a new pseudo-random fixed-point code every clock. With a small illustrative width of four, seed `1011`, and tap mask `1100`, the update rule used by the RTL gives:

```text
1011 -> 0111 -> 1111 -> 1110 -> ...
```

The shared-LFSR architecture compares every X lane with the current LFSR code. D compares against the same sequence delayed by exactly two clocks, decorrelating the two pulse vectors without a second LFSR.

Because the LFSR advances even while an architecture captures or drains a frame, different downstream latencies can shift the random phase seen by later frames. Each LFSR architecture is therefore checked against its own cycle-accurate expected stream.

## Pulse generators

All normalized values are unsigned fixed-point codes in `[0,1]`. A pulse is generated by the exact comparison `random_code < input_code`; equality produces no pulse.

For four lanes listed as `[lane0, lane1, lane2, lane3]`:

```text
input codes:          [2, 7, 12, 15]
independent random:   [3, 6, 12, 1]
output pulses:        [0, 1, 0, 1]
```

`PULSE_GENERATOR` accepts a separate random code for every lane. `PULSE_GENERATOR_LFSR` uses one shared LFSR code for all lanes; with shared code `7`, the same input produces `[0, 0, 1, 1]`. This shared comparator input saves random-generation state and routing area, while the independent version avoids coupling between lanes.
